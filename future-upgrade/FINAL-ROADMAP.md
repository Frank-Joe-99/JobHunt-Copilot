# JobHunt-Copilot 最终开发路线 v1.0

更新日期：2026-10-26  
适用范围：当前本地优先的 CLI / MCP 项目，按单人或小团队维护成本设计。  
文档状态：融合[初版路线](INITIAL-ANALYSIS.md)与[可行性审核](Adverse.md)后的实施基准。两份原文保留作为讨论记录，开发顺序以本文为准。

当前进展：前三批 M01～M09 均已实现，完整回归为 157 项。第一、二、三批记录分别见 [M01～M05](BATCH-1-IMPLEMENTATION.md)、[M06～M07](BATCH-2-IMPLEMENTATION.md)、[M08～M09](BATCH-3-IMPLEMENTATION.md)，总览见[完整升级目录](UPGRADE-INDEX.md)。M09 通过可选 `--flow adaptive` 提供，默认保留 fixed；真实模型的质量、成本和延迟仍需成对验证。M10～M12 仍为后续规划。应用测试使用合成材料、临时目录和模拟服务，没有读取真实个人配置或调用真实模型、GitHub。

## 1. 最终取舍

**先修复信息传递、内容定位和模型兼容，再建设可恢复的面试，最后试点受控自适应。**

对规模较小的候选人档案，默认输入经过字段白名单处理的完整业务材料，让模型根据岗位判断重点；暂不建设事实图谱、向量库或复杂检索系统。对实时面试，优先保持单次调用与流式体验；对批量定制，保留现有一键工作流和复合 MCP 工具。

评测贯穿每项修改：先用少量合成案例复现问题，随修复增加回归检查；不把完整评测平台当作开工前提，也不推迟到全部重构完成之后。

近期可以交付一个有独立价值的版本：

- 同一候选人面对不同 JD，能够得到有根据的定向改写。
- 改写准确落在对应经历，能够查看差异，主档案保持独立。
- 面试领域由目标岗位决定，缺失事实不被默认补齐。
- 已选择的模型参数可用，推荐服务失败不影响简历主流程。
- 现有 CLI 与 MCP 用法保持兼容。

## 2. 回顾原有设计和上一版路径

项目原有路径是：结构化 YAML 档案 → 独立业务 handler 与固定 prompt → 核心流水线协调 → CLI / MCP 使用 → 本地文件或 SQLite 保存。

这种设计让功能容易理解、单个模块容易调用。当前主要瓶颈是调用链传递的信息不完整、改写定位脆弱、领域与风格绑定、会话只在内存中，以及客户端对模型能力区分不足。

上一版的主顺序是：建立评测基线 → 修复信息链 → 自适应面试 → 可审查的简历修改 → 模型与工具演进 → 体验扩展。本次将内容定位和最小模型兼容前置，先实现会话恢复，再做自适应；评测保留但随开发增长，避免一次建齐案例库。

上一版提出了 A～H 八条路线。本次保留目标，缩小首版实现范围：

| 原路线 | 保留的价值 | 最终调整 |
| --- | --- | --- |
| A：任务契约式 prompt | 明确目标、事实边界，分离领域与风格 | 最先做；保留兼容模板，不按模型大小自动认定哪套更好 |
| B：上下文与证据 | 让岗位要求和候选人材料贯穿流程 | 先传完整业务材料和简单来源引用；复杂证据库后置 |
| C：自适应面试 | 根据回答决定追问或换题 | 放到兼容性与会话恢复之后；单次调用、小决策、预算兜底 |
| D：简历修改提案 | 准确定位、差异可查、事实可追溯 | 前置定位修复；生成批量草稿，不逐条弹确认 |
| E：模型能力适配 | 新模型能够真正进入系统 | 拆成早期参数修复与后续结构化输出适配 |
| F：MCP 演进 | 灵活复用宿主推理和本地工具 | 复合工具为主，少量基础工具按需新增 |
| G：推荐证据验证 | 不虚构文件路径与学习路线 | 先缓存、限额和降级；只对少量候选补证据 |
| H：持久化与练习闭环 | 重启可恢复、练习可延续 | 先保存会话与操作状态，长期能力记忆后置 |

## 3. 对审核意见的采纳与修正

审核提出的资源约束很有价值，但其中一些确定性表述超出了源码或资料能够支持的范围。本节给出最终裁定，避免把风险提醒写成新的硬编码假设。

| 议题 | 最终裁定 |
| --- | --- |
| 30 个案例前置是否过重 | 采纳减负意见。先建立 5 组小型基准场景，修复时补必要检查；后续按失败案例扩充。 |
| 小档案是否需要检索系统 | 采纳简化意见。先传经过最小化处理的完整业务材料；不假定所有档案都是固定 token 数，也不承诺固定调用成本。 |
| 客户端参数修复是否应前置 | 采纳。最小兼容修复提前，完整多端点适配不与首批改动捆绑。 |
| 结构化决策是否必然导致长时间静默 | 保留延迟风险，修正必然性。Structured Outputs 支持流式处理；实际能否流畅展示取决于具体模型、端点和实现，不能直接采用审核中的秒数作为测量结果。 |
| 是否只凭模型名过滤 temperature | 不采纳。名称包含某字符串不能可靠代表能力，代理别名尤其如此；采用明确能力配置和可解释的兼容错误。 |
| 任意 400/500 是否都应降级 JSON 格式 | 不采纳。格式不支持、schema 写错、鉴权失败、暂时性服务故障必须区分，不能无差别重试或削弱约束。 |
| GitHub 无认证配额风险 | 采纳预算与缓存。60 次/小时是无认证 REST 的主限额，搜索还有限制，不能只按一个总数设计。 |
| GitHub 限流是否必然阻断全部流程 | 修正。当前定制流程捕获推荐异常，推荐也有容错；岗位雷达本身不调用 GitHub。需改善状态呈现，不能说它必然中断全部流水线。 |
| 读取 README 是否等于验证了具体文件路径 | 不采纳。只有 README 明确支持或已实际查询存在的路径才能作已验证引用；否则给模块级路线并标明未验证。 |
| PDF 检查是否需要先加新依赖 | 修正。项目已经依赖 `pdfplumber`；中文提取异常仍可能发生，结果用于诊断，不能等同某招聘平台的 ATS 判断。 |
| `proj_0_hl_1` 是否天然是永久稳定 ID | 修正。索引在重排后会变；首版只在冻结快照内定位，配合版本校验。跨快照身份另行设计。 |
| 面试是否应立即共用 tracker 数据库 | 采纳 SQLite 持久化，调整为独立会话库优先；避免为复用数据库跨业务模块 import，也减少迁移对投递看板的影响。 |
| MCP 原子化是否应替代复合工具 | 不采纳替代方案。保留实际存在的 `tool_one_click_tailor` 等复合工具；调用次数、费用和授权提示取决于宿主，不能预设固定倍数。 |

GitHub 的配额与响应头处理以其[官方限流文档](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)为准；结构化结果可以增量处理的依据见 [OpenAI Streaming 说明](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses#streaming)。上表其余修正来自项目源码复核或本文的实施取舍。

## 4. 按难度与可行性排序的工作包

难度分为 1～5：1 是局部改动，3 涉及状态或外部协议，5 涉及新的交互产品与运行条件。“高可行性”表示可以用当前技术栈小步交付，不表示已经验证效果。

排序在满足依赖的前提下，优先考虑低难度和明确收益；如果所选模型当前无法调用，M04 应先于需要在线验证的任务完成。后面的扩展不构成前面版本的发布条件。

| 顺序 | 工作包 | 难度 | 可行性 | 直接收益 / 主要前置 |
| --- | --- | ---: | --- | --- |
| M01 | prompt 去偏见与事实默认值清理 | 1 | 高 | 避免问错领域和补造背景；无复杂前置 |
| M02 | JD 与匹配结果贯穿润色、面试 | 2 | 高 | 定制真正使用岗位差异；沿用核心数据契约 |
| M03 | 快照内按 ID 修改与批量差异报告 | 2 | 高 | 修复错改、漏改；新增最小定位字段 |
| M04 | 模型参数与结束状态的最小兼容 | 2 | 高 | 支持目标模型，识别不完整响应；明确配置 |
| M05 | 编排边界与“已准备/已投递”语义修复 | 2 | 高 | 减少架构耦合和失真的看板记录 |
| M06 | 开源推荐的预算、缓存与分级证据 | 3 | 高，受网络条件影响 | 网络不稳定仍可完成主任务；有限外部请求 |
| M07 | 面试会话持久化与重试一致性 | 3 | 高 | 重启恢复、避免丢答和重复状态变更 |
| M08 | 结构化输出分层适配 | 3 | 有条件 | 提高结构可靠性；依赖 M04 和目标端点实测 |
| M09 | 单次调用的受控自适应面试 | 4 | 有条件 | 有针对性的追问；依赖 M01、M02、M04、M07 |
| M10 | 少量 MCP 基础工具与宿主协作试点 | 4 | 有条件 | 专家流程可组合；先有稳定核心服务 |
| M11 | 长期练习记忆与超长材料检索 | 4 | 需求触发后实施 | 跨次练习有延续；先有可靠会话与用户反馈 |
| M12 | 本地界面、语音和岗位采集等扩展 | 5 | 分项验证 | 扩大使用场景；核心体验稳定之后单独立项 |

轻量回归检查、事实边界、隐私和日志要求贯穿 M01～M12，不另设一个昂贵的“平台建设阶段”。

## 5. 第一阶段：用小改动交付可靠的定制与通用面试

### M01：prompt 去偏见与事实默认值清理

主要位置：[面试 prompt](../skills/mock_interviewer/prompt.py)、[面试 handler](../skills/mock_interviewer/handler.py)、[推荐 prompt](../skills/project_recommender/prompt.py)。

- 将“严苛/务实/亲和”的风格与技术领域分离，领域来自岗位或 JD。
- 清理“缺少角色就写核心开发”等事实性默认值；档案加载失败时报告具体问题，首版不自动塞入示例学历。
- 保留“一轮一个核心问题”和用户退出权；讲解限制只适用于模拟模式。
- 删除没有检索证据却强制输出精确仓库文件路径的要求。
- 保留兼容模板，只有对目标模型的案例验证显示必要时才加具体示例；首版无需建立自动模型分类器或大型模板引擎。

**验收**：前端、后端和研究岗位的上下文各自正确；配置错误不会被匿名假档案掩盖；未知贡献仍保持未知。prompt 中没有错误领域，并不证明模型一定不会离题，语义表现仍要抽查。

### M02：把已有信息传递完整

主要位置：[工作流](../core/workflow.py)、[润色 handler](../skills/resume_polisher/handler.py)、[JD handler](../skills/jd_matcher/handler.py)、[核心数据契约](../core/state.py)。

先为 `polish_experiences` 增加可选的岗位上下文参数，传入现有 `JobDescription`、原始 JD 和 `MatchResult`。参数设计保持旧调用兼容；跨模块只传核心数据对象，不增加业务模块之间的 import。

面试和匹配默认接收完整的教育、技能、实习、项目、科研等必要业务材料，移除无依据的“只取前几条”。姓名、联系方式、照片、密钥等不因“全量输入”而一并发送。模型生成的匹配建议标为分析结果，不能反过来当候选人事实。

设置可配置的上下文预算：输入过大时明确提示，或采用保留来源和限定词的分段方案；不静默丢掉后面的经历。只有实际材料规模或评测显示需要时才实现检索。

**验收**：同一候选人、同名岗位、不同 JD 的请求包含对应要求；排在后面的相关经历可以被看到；业务输入不包含无关联系方式。

### M03：快照内定位改写，批量生成可查看草稿

主要位置：`core/state.py`、`core/workflow.py`、润色 handler 与 prompt。

首版不改变用户 YAML 中 `highlights: list[str]` 的写法。加载后冻结一个内存快照，给亮点建立该快照内的定位表。修改提案至少带：

```json
{
  "snapshot_id": "synthetic_snapshot_01",
  "target_ref": "projects[0].highlights[1]",
  "expected_original_hash": "digest_of_original_text",
  "polished": "根据已提供事实形成的建议文本",
  "needs_confirmation": false
}
```

这是合成接口示意。实际应用时校验快照、允许修改的目标、原文摘要和重复目标；不能把模型返回的路径当任意对象访问表达式执行。

索引只在对应快照内有效；发生重排或重新加载就重新校验。以后确实需要跨次追踪时再增加持久 UUID，不能将临时索引误当永久身份。

通过检查的提案批量应用到定制草稿，并生成原文/改写/理由/待确认项的 Markdown 对比，保留原始快照。无需逐条 y/n。合法定位只能证明改对了位置，不能证明句子真实；新增数字、职责扩大和完成状态变化仍要检查。存在重大事实疑点时标为待核实草稿，不展示成可直接投递版本。

**验收**：两个项目存在相同原文时仍只修改指定项；未知目标、过期快照、重复修改被拒绝；真实主档案未改动；不再静默回退到原文字符串匹配。

### M04：先做最小客户端兼容

主要位置：[LLM 客户端](../tools/llm_client.py)、`core/state.py`、[配置示例](../config/settings.example.yaml)。

- 让采样参数可以明确省略，按端点与模型的能力配置决定发送哪些参数。
- 明确输出预算字段和限额；去掉统一的 8192 截断假设，同时保留任务预算与模型上限检查。
- 首批只验证项目实际需要的端点与模型配置，不一开始覆盖所有供应商和新 API。
- 记录完成、截断、拒绝、网络失败等状态，不能只返回 content 然后丢弃结束原因。
- 分别处理鉴权、参数不支持、限流和临时故障；输出必要元数据，避免日志带出完整请求、档案或密钥。

能力配置与缓存至少按端点、模型和协议模式区分，不能用名称里是否有 `r1` 或 `o3` 替代验证。不自动迁移用户真实配置；只更新 example 模板和默认兼容逻辑。

**验收**：模拟请求能验证该省略的参数没有发送；配置错误可定位；截断不被判为完整成功；已有已支持配置不回归。

### M05：修正编排边界和业务状态

将岗位雷达调用 JD 匹配的协调逻辑移到 `core/`。业务模块只处理本模块职责；现有 CLI、MCP 和公开入口通过兼容门面保持可用，避免只把跨模块 import 藏到另一个 handler。

“生成物料”和“已经投递”采用不同语义。首版可以不自动创建投递记录；确需保存准备情况时使用明确的准备标记或现有心愿单，不把导出成功自动记成 `APPLIED`。用户明确报告已提交后再推进状态。任何默认行为或 CLI 参数调整，同步更新相关 Skill、说明与 MCP 行为。

PDF 文本提取可用已有 `pdfplumber` 做非阻塞诊断；异常标为解析问题，保留视觉复核途径，不据此宣称招聘 ATS 拒绝。

**验收**：无业务模块跨模块 import；雷达排序行为兼容；单纯导出不会增加“已投递”数量。

**第一阶段发布条件**：M01～M05 对应回归检查通过，至少完成一组“同档案、不同 JD”的人工成对检查。此时即可交付，不等待自适应面试或完整能力适配器。

## 6. 第二阶段：保证外部依赖可退、面试状态可恢复

### M06：给推荐设置预算、缓存和证据等级

主要位置：[GitHub 客户端](../tools/github_client.py)、[项目推荐](../skills/project_recommender/handler.py)、报告组装。

1. 缓存公开仓库元数据、README 与已验证引用，保存来源时间和版本；缓存中不混入候选人档案或 JD。
2. 对搜索次数、补充请求、下载体积和总耗时分别设预算。首版可以最多补取 2 个候选 README，具体数量可配置。
3. 参考响应中的剩余额度、重置时间与重试提示，并处理搜索限制；不把所有 403 当配额耗尽，也不不断重试。
4. README 足以支持模块级建议时就停止。精确路径必须有明确引用或额外的定点存在性检查，额外请求也计入预算。
5. 默认不遍历全仓；无证据时降低建议精度，不降低事实要求。
6. 无网或限流时采用有日期的缓存，或者跳过推荐继续生成简历。

报告区分“用户关闭”“服务不可用”“未找到合适项目”“已完成推荐”。当前部分缺省文案会把未生成推荐解释成没有技能缺口，应同时修正。

预置离线项目清单可选，但会产生维护成本；未检验的新版本路径和过期星数不能冒充实时结果。不把配置 Token 设为基础功能的必要前提。

**验收**：重复请求命中缓存；预算耗尽后停止外部读取；限流不阻断简历生成；未知文件不会被展示为已验证路径。

### M07：面试会话持久化和一致性

建议默认使用 `storage/interviews.db`，独立保存会话。选择 SQLite 是沿用现有技术栈；选择独立文件是减少看板耦合，不需要新增数据库服务。

存取职责放在面试模块或核心服务中，基础连接工具可放 `tools/`；禁止面试模块 import 投递模块。CLI 和 MCP 共用同一个会话服务，进程内字典至多作缓存。

首版保存会话 ID、schema 版本、岗位上下文、输入事实快照、问答和运行状态。用不会因同一秒启动而冲突的 ID；新表有明确版本处理，不假定现有 `CREATE TABLE IF NOT EXISTS` 已提供升级迁移。

处理一次回答时：

- 先保存回答和请求标识；
- 模型生成的问题处于 pending，完整成功后再提交阶段变更；
- 流中断时标记失败或部分输出，重试不重复登记用户回答；
- 同一会话并发更新使用版本检查或锁，不在等待网络期间长期占用数据库写锁；
- 报告只使用已接受的完整记录，恢复时校验 schema 和事实快照。

当前 handler 在 `finally` 中登记已收到的问题片段，这一点应随持久化一起处理；否则部分输出可能被恢复成完整题目。

**验收**：重启能够读取同一会话；中断不丢已提交回答；重复请求不重复写入；并发不会静默覆盖；迁移失败不损坏已有投递数据库。

暂停/恢复或 `session_id` 等新入口若影响 CLI，必须同步更新仓库 Skill 中引用的命令。私有会话继续被 Git 忽略，并提供可查看和删除的方式。

## 7. 第三阶段：在可测的边界内增加模型决策

### M08：结构化输出分层适配

依赖 M04。优先使用目标端点已验证支持的原生 schema；否则使用 JSON mode 或 prompt JSON，并始终做核心数据校验。

```text
按已知能力选择输出方式
  → 仅在确认该格式不受支持时尝试兼容方式
  → 校验结构与业务条件
  → 在同一请求预算内有限修正，或返回明确失败
```

schema 本身有错就修代码；鉴权失败就报告配置问题；拒绝不通过格式降级绕过；网络和限流按对应策略处理。不要让每次请求都先试一遍必定失败的模式，兼容信息应能缓存且允许失效。

JSON 修复结果保留“修复/不完整”状态。被截断的报告不能因为能解析就自动进入正式结果。重试有总次数与总耗时限制，已经向用户展示的流式内容不静默重播。

**验收**：模拟端点不支持格式、schema 错误、拒绝、截断和服务故障时，走不同的预期路径；降级不扩大数据外发范围，不绕过业务校验。

### M09：受控自适应面试

依赖 M01、M02、M04、M07。M08 提供输出能力适配，但不要求所有端点必须支持原生 schema；最小决策经过校验即可试点。

首版保留阶段作为覆盖路标，每轮尽量只调用一次模型，返回较小的动作和问题：

```json
{
  "action": "clarify",
  "question": "你刚才说参与了这个模块，能具体说明你亲自完成的部分吗？"
}
```

这是合成示例。动作可包含追问、澄清、换阶段、反问回应、结束；能力引用等字段仅在使用场景需要时补充。完整的能力评分与训练建议放到复盘，不在实时路径串联多个评审模型。

程序处理全局时长/轮数、连续追问上限、重复问题和退出指令。连续追问最多 2 次可以作为试验参数，但上限是兜底，不是要求每道题必须问够两次。覆盖不足时优先换到关键能力；没考察到的内容标“未观察到”。

区分模拟与训练：模拟时保持考官视角，训练时允许提示、讲解与重答。公司内部情况不可编造；参考回答不能替候选人补造个人经历。

流式展示由已验证的端点事件或解析器支持；业务状态只在最终结果完整后提交。首版不要用容易破损的特殊标记分割文本来冒充可靠协议。无法满足交互等待目标的模型可以用于离线复盘，实时提问继续使用已验证配置。

**验收**：

- 追问实际使用了上一轮回答，充分回答后不会无意义地纠缠。
- 用户可以跳过、暂停或结束；错误不能造成无限循环。
- 记录首个可读问题出现时间、总耗时、失败/重试率与调用数；进度提示不算首个问题。
- 与原流式模式做同输入、同预算的质量和延迟对比，达到预先约定的接受标准才调整默认行为。

保留旧流程回退开关，试验失败不影响既有快速面试。

## 8. 第四阶段：由真实需求触发的扩展

### M10：复合 MCP 工具为主，基础工具为辅

保留现有 13 个工具的主要契约和 `tool_one_click_tailor` 等入口。基础工具只为已经出现的需求增加，例如读取恢复会话、批量保存定制修改、查看有限范围的业务证据。

宿主负责推理和项目内部负责推理都可以试验，先比较完整任务耗时、结果质量、调用数和实际授权体验。不能仅为了减少内部 LLM 调用，就要求普通用户完成更多工具交互。

增加或改变工具时同步更新类型、注解和协议测试；写操作提供请求幂等性或版本校验；stdout 继续只承载协议。

### M11：长期练习记忆和按需检索

只有用户确实需要跨次复习，或材料超过已配置上下文预算时再投入。

先保存可追溯的“某次回答暴露的待练习点”，允许用户纠正和删除，不把模型评分固化成永久能力标签。先尝试全文和结构化过滤；出现实测的材料容量或命中问题，再评估向量检索或更细粒度证据模型。

不要求用户为此重写原有 YAML。历史事件、摘要和判断分开存，重要结论能回到原问答。

### M12：交互与采集扩展分别立项

本地界面、语音、自动岗位采集是不同产品工程任务，不合并成一个“大改版”。

界面先解决差异查看、会话恢复和报告导航；语音增加转写纠正、打断与设备适配，不能把技术名词转写错误直接算能力失分；岗位采集先解决来源、去重、过期信息和失败恢复，再考虑定时通知。

这些功能均不阻塞前面各阶段交付。完整多模态平台、多代理编排和微调均不是近期目标。

## 9. 轻量评测：随开发增长

### 9.1 五组起始场景

每组可以先只有一个最小合成样例，再围绕发现的问题增加变体；不追求一次建成全面的案例库。

| 场景 | 首先检查什么 |
| --- | --- |
| 同一档案、两个不同 JD | JD 与匹配信息是否完整传递；人工确认建议确有岗位差异 |
| 重复亮点与过期快照 | 指定项是否准确修改，非法或过期提案是否被拒绝 |
| 不同岗位与缺失事实 | 前端/后端/研究领域是否解耦；未知信息是否被保留 |
| 不同模型响应与外部失败 | 参数兼容、拒绝/截断、推荐限流、JSON 模式不支持 |
| 会话重启、中断、并发与重试 | 已提交回答不丢失，阶段不越界，数据库不重复或相互覆盖 |

相关场景随 M01～M09 实现逐步启用，不要求在 M01 前就把恢复和自适应测试写完。

### 9.2 区分确定性测试与生成质量

确定性回归使用临时数据库、临时输出、合成配置和可控模型/HTTP 替身；不得直接使用用户默认档案、真实看板或 API Key。现有测试尚未做到全部隔离，先为受影响链路补测试入口，不必先重写所有测试。

默认 CI 不请求付费模型、不依赖实时 GitHub。真实模型对比单独运行，并记录实际版本、端点、prompt 版本和已知预算。

字段、ID、状态和协议可以自动断言。关键词命中只能证明信息出现过，不能证明推理正确或追问有价值。生成质量先做少量人工成对比较，必要时增加经人工校准的模型评分；不要把整段固定答案当金标准。

### 9.3 每个版本的发布条件

- 受影响的确定性用例与必要协议检查通过。
- 关键案例没有无来源的重大数字、职责或完成状态。
- 修改主档案、外部提交、看板推进与用户真实意图一致。
- 记录质量收益和成本/延迟代价，重要退化有明确处理。
- 对状态迁移和默认行为变更，有兼容说明和回退方法。

先记录基线再约定量化门槛；本文不采用未经测量的固定等待秒数、提升百分比或“全部场景必然正确”的结论。

## 10. 可直接执行的开发批次

| 批次 | 包含工作 | 完成后能交付什么 | 可以暂不做什么 |
| --- | --- | --- | --- |
| 第一批 | M01～M05，随改动补相应回归 | 可靠的岗位定制、准确改写和通用面试基础 | 会话库、原生 schema、全面评测平台 |
| 第二批 | M06、M07 | 网络服务失败可退、面试重启可恢复 | 自适应面试与新界面 |
| 第三批 | M08、M09 | 在预算和延迟约束内的自适应面试试验版 | 全自动多代理、长期画像 |
| 后续批次 | 按需求选择 M10～M12 | 专家协作或产品体验扩展 | 未被需求与数据证明值得做的功能 |

第一批建议拆成至少五个独立可审查变更，分别处理 prompt、JD 传参、定位改写、客户端兼容、编排与状态；编排清理和状态语义也可以再拆。每个变更保留既有接口的兼容路径，不一次替换所有模块。

配置新增字段采用可选项与兼容默认，只修改 `*.example.*` 模板。私有配置、简历、报告、数据库和临时文件不提交。若修改 CLI 参数或默认用法，同步更新相关 `.agents/skills/*/SKILL.md`。

**前三批实现及确定性测试已完成；下一步是目标端点的成对质量与延迟验证，再按需求选择 M10～M12。** 不把尚未实测的自适应收益当作默认升级依据。完整阅读入口见[升级目录](UPGRADE-INDEX.md)。
